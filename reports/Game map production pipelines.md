# Shipped games derive maps from level data

Wherever a production pipeline is actually documented, the player-facing map is derived from the same data the level is built from, and the only map-specific authoring is a small reusable style layer: a glyph table, a colour table, an icon list or a material theme. Nintendo generated *Breath of the Wild*'s map textures procedurally and rebuilt every section nightly; Diablo draws its automap at run time from a per-tileset lookup; Blizzard, Valve and Relic editors bake a top-down image on save, export or command. Hand illustration is real (Assassin's Creed Mirage credits a named map artist) but its production and maintenance process is undocumented for every illustrated map studied, so "hand-painted" mostly describes a look, not a confirmed pipeline. The recurring failure across studios is not generation but coexistence: regenerated images clobber hand edits, go stale after geometry changes, or come out blank. The data a map needs is small and stable across genres: a base raster or cell grid, a world-to-map transform, static icons, labels, region or room definitions, a discovery mask at map resolution, and a floor or layer index. Engines ship only the primitive (a second camera rendering to a texture); the one out-of-the-box system that styles a map from layout data is Dungeon Architect's Dungeon Canvas. No shipped game was found using an image model to stylise its map, and the one rigorous published study shows the known problems: fake labels, seams, blur and no registration metric.

Evidence flags used throughout: **(snippet)** means the claim was seen only in a search-engine extract of the page, not the page body; **(inference)** means reasoning from behaviour, not a documented fact; **(unconfirmed)** means no source settles it. All four research notes were single-pass studies, and absence of a source is not proof of absence.

The *Breath of the Wild* facts come third-hand (CEDEC 2017 talk, Japanese press, English summary), and the CD Projekt RED page was readable only as search extracts.

The layer set is nearly constant across these games; what varies is cartographic idiom and discovery granularity. Three granularities appear: per-region unlock (*Breath of the Wild* towers), per-region detail over an always-visible base (*Elden Ring* fragments), and continuous reveal along the player's path (*Ghost of Tsushima*). Sync cost follows production method (inference): a fully generated map syncs on a nightly job, a captured-then-adjusted map needs repeated manual work, and an illustrated map needs an artist to redraw the changed area. Only the first two are documented. Nintendo's team also plotted task and bug data on the same map, which shows the world-to-map transform is worth having as a production tool in its own right ([CEDEC summary](https://gist.github.com/idbrii/e39fe96279aa1670319bfa521d907399)). Minimap rotation and how minimap imagery relates to world-map tiles are undocumented for every game here.

## Automaps: the generator's own grid is the map

In dungeon crawlers, roguelikes and metroidvanias the best sources are reverse-engineered code and modding documentation, and they agree: no documented automap is drawn independently of level data. Three models recur, distinguished by map resolution relative to level resolution: per collision tile, per screen, and per room.

| Game | What the map shows | How it is produced | How it is kept in sync | Source |
|---|---|---|---|---|
| Diablo (1996) | Wall outlines, doors, arches, grates, stairs, floor dots on the dungeon cell grid | Run-time line drawing; a **512-entry tile-to-glyph table per tileset** (`.AMP` file) gives a shape type plus door, arch, grate and stairs flags | Automatic: no per-level map asset exists; explored state is a boolean per cell, with neighbour rules so bounding walls appear | [devilution automap.cpp](https://github.com/diasurgical/devilution/blob/master/Source/automap.cpp) |
| Diablo II | Small pre-drawn sprites per tile | `AutoMap.txt` rows match level type, tile orientation and style, then pick one of up to four `MaxiMap.dc6` frames | Automatic via tile identity | [D2 Data File Guide](https://d2runewizard.com/game-files/guide.html) |
| Super Metroid | Coarse grid, one cell per screen-sized scroll block; station-revealed cells blue, visited cells pink | Hand-authored area tilemap; each room stores its X and Y on the area map | **One explored bit per map cell, 256 bytes per area**; "map station obtained" is a separate byte per area | [RAM map](https://patrickjohnston.org/ASM/Lists/Super%20Metroid/RAM%20map.asm); [Metroid Wiki](https://metroid.fandom.com/wiki/Map) |
| Binding of Isaac / Rebirth | Room-per-cell grid with special-room types; Rebirth adds multi-cell rooms | The generator's 9x8 occupancy grid already holds everything the minimap needs; doors are implied by adjacency | Automatic. | Dead Cells | Explored-tile minimap (behaviour only) | Levels are hand-made room templates placed on a designer graph; the minimap pipeline is not described. Rendering from the collision grid is (inference) | Unconfirmed | [Deepnight](https://deepnight.net/tutorial/the-level-design-of-dead-cells-a-hybrid-approach/) |
| Hollow Knight | Area maps bought from a vendor; rooms added only on resting at a bench with the Quill; pins bought separately | Internals unconfirmed; one sprite per room is (inference) | Deferred commit of visited rooms (behaviour) | [Hollow Knight Wiki](https://hollowknight.wiki/w/Map) |
| Metroid Dread | Detailed room outlines, item icons with collected state, colour-coded doors, ability-to-door highlight, six player markers | Undocumented | Undocumented | [Nintendo Dread Report 3](https://metroid.nintendo.com/dread/news/metroid-dread-report-vol-3) |

Two run-time strategies cover every documented procedural case: a tile-to-glyph lookup at draw time, and drawing the generator's room-occupancy grid with a type icon per room. Both need zero per-level authoring, because the authored cost is per tileset, not per level. The price is context sensitivity: Diablo patches some glyphs in code depending on neighbouring tiles ([devilution](https://github.com/diasurgical/devilution/blob/master/Source/automap.cpp)). A second pattern recurs in *Super Metroid*, *Hollow Knight* and *Prey*: "the player owns the chart" and "the player has been there" are stored separately and combined at draw time. No documented shipped example of radius-based reveal was found; *Path of Exile*'s walkability overlay and *Diablo IV*'s missing overlay map are (snippet) only.

## Strategy minimaps: baked on save, and the bake clobbers hand edits

Strategy, RTS and MOBA minimaps split into a static background, an authored icon overlay stored as data, live markers and a fog layer. The background and icon overlay are directly evidenced; live unit markers, pings and the camera box are observable in play but were not sourced.

"Regenerate on every save into a reserved filename" is the dominant design, and its failure mode repeats across three studios: clobbered hand art or a silently blank image. The designs that cope keep generated and authored images under distinct names with an explicit precedence rule. Riot's fog design is the cleanest sync guarantee found: the minimap is a second consumer of the same visibility mask as the world, so the two cannot disagree, and raising the grid to 256x256 was rejected because it would have quadrupled CPU cost ([Riot](https://www.riotgames.com/en/news/story-fog-and-war)). Readability is a colour-budget problem: background colours must not collide with team and resource colours (inference from modder and player discussion, snippet).

The lesson is mostly negative. *Control* shows that a single top-down projection of a stacked building is unreadable without floor slicing, and that streaming the map late is itself a usability bug. *Resident Evil 2 Remake* shows what the richer model buys: rooms, doors and items as first-class map entities with their own state. ## Image-model stylisation: one rigorous study, no shipped game

No documented shipped game uses a diffusion model to produce its player-facing map from game data; this is absence from a short search, not proof. The one directly relevant published case is Affolter et al. from ETH Zurich, who train ControlNets on Stable Diffusion 1.5 using colour-coded vector rasters as the control image, with **512x512 tiles**, one RGB colour per feature class, four released checkpoints for Swiss cartographic styles, and a user study with professional cartographers ([arXiv 2508.18959](https://arxiv.org/abs/2508.18959); [code](https://github.com/claudaff/generative-ai-mapmaking)). Structurally this is the game problem, with one decisive difference: they had thousands of aligned vector-to-map pairs from a national mapping agency, and a game project has no such corpus for its art style (inference). The only game-adjacent demo found is a 2023 practitioner pipeline that projected Stable Diffusion plus Multi-ControlNet output onto colour-coded Houdini layouts for isometric maps, with no limitations reported ([80.lv](https://80.lv/articles/using-houdini-stable-diffusion-multi-controlnet-to-create-isometric-maps)).

The documented problems are specific. Labels: unless text is masked in both raster and vector training data, the model emits illegible fake lettering, so labels must come from a separate process. Alignment: the authors state "the better the alignment between target and source, the better the resulting model", and misaligned historical data gives poor tiles. Scale: tiles trained at 1:5000 are expected to blur at 1:25000. Non-determinism: several seeds are generated per tile and the best is chosen automatically with a segmentation model. Stitching: the repository says only that tiles "can, if needed, be stitched" ([GitHub](https://github.com/claudaff/generative-ai-mapmaking)); a secondary summary lists stitching and topology as open issues (snippet). Tiled-diffusion tooling reports visible seams "particularly on smooth single-color regions" (snippet, [InvokeAI PR 6635](https://github.com/invoke-ai/InvokeAI/pull/6635)), which is exactly what sea and parchment are (inference). Coastline or road displacement and invented features are widely assumed but were not found quantified anywhere.

No published registration metric for stylised maps was found. The study validates with pixel MSE against a paired ground-truth tile, which it warns only makes sense with perfectly corresponding data. A workable measure can be assembled from standard parts (inference): re-segment the stylised output into classes and compute per-class IoU against the source raster, add centreline distance statistics for coasts and roads, and count unmatched features. For a game an invented bridge is a functional bug, not a blemish (inference).

## What a map system needs, and who authors it

The table consolidates the data layers the documented systems imply. No developer publishes a schema; the "evidence" column shows where each layer is directly observed.

| Layer or metadata | What it holds | Evidence | Status |
|---|---|---|---|
| Ground or terrain class | Class per cell or tile, mapped to a colour or glyph through a small table | AoE II `terrain_id` to colour (snippet); Diablo tile-to-glyph table | Documented |
| Relief | Height field for contours, tint or hachures | BotW contour and hypsometric map | Shown; generator inputs unconfirmed |
| Water | Water mask, optionally depth | BotW bathymetric colouring; W3 exterior layers (snippet) | Shown |
| Roads | Road network on the base map | BotW, Elden Ring base, W3 layers (snippet) | Shown; raster versus spline representation unconfirmed |
| Footprints and rooms | Building footprints outdoors; room polygons or cells indoors, with room type | BotW buildings; Isaac room grid; RE2 rooms | Grid documented; polygons inferred |
| Doors and links | Door position, the rooms joined, lock kind; stairs and elevators with target floor | Diablo door flags; RE2 lock annotations | Flags documented; link records inferred |
| POI icons | Id, type, position, optional orientation, state enum, visibility conditions, per-icon tint | Warcraft III icon file (snippet); BotW three-state icons; Dungeon Canvas icon list | Documented |
| Labels | Text, anchor, feature class, min and max zoom, optional visited gate | BotW zoom-dependent labels | Behaviour documented; table inferred |
| Regions | Area polygons or a tile-to-area index driving reveal and region labels | BotW area definition file beside map textures ([zeldamods](https://zeldamods.org/wiki/Content/UI/MapTex)) | Existence documented; format unknown |
| Discovery state | Bitmap or boolean grid at map resolution, or flag per room or region; saved per playthrough | Diablo, Super Metroid, LoL fog grid | Documented |

| Entity state | Per-room cleared status, per-door seen and lock state, per-item seen and collected | RE2 behaviour | Inferred from behaviour |
| World-to-map transform | Affine mapping from world coordinates to map pixels, stored with the image: playable bounds, tile origin and size, capture depth | Dota 2 boundary entities (snippet); CoH2 `minimap_size`; Super Metroid per-room map X and Y | Documented in strategy; inferred for open world |
| Floors and layers | Layer index, name, own imagery and transform; height range to pick the current floor | Elden Ring overworld and underground toggle; Control as counter-example | Layers documented; height ranges not documented anywhere |
| Raster pyramid | Tiles keyed by layer, zoom, x, y, streamed by section | BotW 120 sections at 4 zooms | Documented |
| Player annotations and live markers | Capped marker lists, path history; entity position and team colour; pings | BotW stamps and Hero's Path; Elden Ring markers | Annotations documented; live markers unsourced |

Commonly automated, by documented example: the base image or geometry (procedural generation, editor capture, tile lookup, or the generator's own grid); regeneration on save, build or nightly job; discovery state and fog; icon placement from entity data; and the transform from map bounds. Commonly hand-authored: the style layer (glyph tables, colour tables, icon art, material themes), which is small and reusable; per-room map coordinates in authored worlds; illustrated world maps where a named artist is credited; post-capture clean-up, as CD Projekt RED and Company of Heroes modders describe; and override images that replace a generated bake. Labels, region boundaries and POI curation are presumably authored as data and placed automatically (inference); no source describes label placement. Unknown for every illustrated map: whether artists paint over a capture or height-derived reference, and how changes propagate.

## Conclusion

The useful dividing line is not hand-made versus generated but where the style lives. In every well-documented system the style is a reusable function applied to data (a glyph table, a colour table, a material stack, a generator), and the map stays correct for free. Where the style lives in pixels, either as a capture that needs clean-up or as an illustration, the sources go silent on maintenance, and the modding record shows the two approaches fighting over the same filename. A new pipeline should treat generated and authored imagery as separate named artifacts with an explicit precedence rule, and keep labels, icons and probably roads as a data-drawn overlay over whatever base is used. That overlay rule is also the main transferable lesson from the image-model work: the model can restyle a base, but text must be removed from its job, and nothing published yet measures whether the coastline it returns is the coastline it was given.

The gaps are concrete and cheap to close. The REDkit minimap page and the Valve minimap page were never read in full and are the two richest primary sources; the remote-sensing map-translation literature was not searched for positional-accuracy metrics; and *Tears of the Kingdom*, *Red Dead Redemption 2*, *Genshin Impact*, Civilization, Total War and *Baldur's Gate 3* were not covered. Conference talks are a poor vein for this topic: map screens are treated as UI plumbing, and the ground truth sits in modding documentation and reverse-engineered code.
